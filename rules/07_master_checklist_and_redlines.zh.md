## ⛔ 十大不可触碰的核心红线 (The Ten Red Lines)

这十大红线是绝对的零容忍底线。无论是人类工程师还是自主 Coding Agent，**只要触犯任何一条，必须立即终止当前任务、阻断 CI 流水线合入**，直至彻底整改完成。

```text
╔════════════════════════════════════════════════════════════════════════════════════╗
║                         十 大 不 可 触 碰 的 核 心 红 线                            ║
╠════════════════════════════════════════════════════════════════════════════════════╣
║  1. 严禁静默瞎猜          需求或架构模糊时，绝不私自做主下注。                     ║
║  2. 严禁无复现改代码      没有编写出可复现的红灯测试前，绝不碰业务代码。           ║
║  3. 严禁顺手重构          绝不夹带格式化、无关注释清理或修饰周围旧代码。           ║
║  4. 严禁接缝泄露          绝不在业务核心层直接导入第三方外部 SDK。                 ║
║  5. 严禁仓库写状态        绝不在 Git 代码库中写入缓存、运行日志或持久化数据。      ║
║  6. 严禁明文打秘钥        绝不在控制台输出或提交历史中暴露未脱敏凭据。             ║
║  7. 严禁破坏性 Git        绝不执行 push --force、reset --hard 或 clean -fd 命令。  ║
║  8. 严禁文档不同步        绝不让中英文双语文档或规范在迭代中产生滞后脱节。         ║
║  9. 严禁盲信模板输出      绝不假设退出码 0 即代表模板渲染毫无静默崩溃。            ║
║ 10. 严禁过度前瞻设计      绝不为一次性场景编写空洞投机的泛型、基类和冗余配置。     ║
╚════════════════════════════════════════════════════════════════════════════════════╝
```

### 红线细则与整改指南

### 1. ❌ 红线 1：严禁静默瞎猜 (No Silent Guessing)
* **违规现象**：在存在多种合理技术选型或业务规则存在歧义时，Agent 悄悄自行选择其中一条开写代码。
* **整改动作**：立即停笔。计算决策前沿（Decision Frontier），单轮打包最多 4 个编号选项，并附带明确的推荐标注与一句话权衡理由。

### 2. ❌ 红线 2：严禁无复现改代码 (No Code Edits Without Repro)
* **违规现象**：遇到 Bug 直接根据直觉去业务代码里改逻辑，连一次稳定复现的失败都没见到过。
* **整改动作**：撤销所有猜测性修改。先编写出能够稳定失败（红灯）的单元测试或最小 CLI 探测脚本。

### 3. ❌ 红线 3：严禁顺手重构 (No Unsolicited Refactoring)
* **违规现象**：在修 Bug 或写功能时，“好心”地顺便把周围无关代码的缩进改了、import 重排了、旧注释改了。
* **整改动作**：剔除所有与当前任务无关的 Diff。确保 Diff 每一行改动均能直接溯源至用户需求。

### 4. ❌ 红线 4：严禁接缝泄露 (No Bleeding Seams)
* **违规现象**：在业务逻辑或表现层中直接 `import` 第三方云服务、支付 SDK 或专用数据库驱动。
* **整改动作**：将第三方依赖封印在独立的适配器后，严格执行**删除测试（Deletion Test）**。

### 5. ❌ 红线 5：严禁仓库写状态 (No State in Code Repos)
* **违规现象**：硬编码相对路径，将运行日志、本地 SQLite 数据库或缓存文件随手写进 Git 目录。
* **整改动作**：使用中心化环境管理器将所有持久化产物与日志分流存入外部独立的数据根目录（Data Root）。

### 6. ❌ 红线 6：严禁明文打秘钥 (No Plaintext Secrets)
* **违规现象**：在控制台、诊断文本或 Git 提交信息中明文打印 Bearer Token、密码或 Cookie。
* **整改动作**：强制引入确定性凭据脱敏流水线，将敏感子串清洗为 `<REDACTED>`。

### 7. ❌ 红线 7：严禁破坏性 Git (No Destructive Force Git)
* **违规现象**：运行 `git push --force`、`git reset --hard`、`git clean -fd` 或 `git checkout .`。
* **整改动作**：在工具层安装纯 Shell 安全拦截护栏，视开发者工作区成果为神圣不可侵犯的资产。

### 8. ❌ 红线 8：严禁文档不同步 (No Documentation Drift)
* **违规现象**：修改了英文文档却留下了落后的中文文档，或者改动了功能却不更新使用指南。
* **整改动作**：在单次 Commit 中原子级同步更新双语文档与规范。

### 9. ❌ 红线 9：严禁盲信模板输出 (No Blind Template Trust)
* **违规现象**：看到页面生成脚本返回 0，就理所当然地以为 HTML 渲染成功。
* **整改动作**：编写自动化断言扫描生成的产物，确保不含 `Error rendering` 等静默异常。

### 10. ❌ 红线 10：严禁过度前瞻设计 (No Predictive Over-Engineering)
* **违规现象**：为一个简单功能凭空创造复杂的抽象工厂、动态插件机制和 10 个未要求的配置参数。
* **整改动作**：严格遵守奥卡姆剃刀法则，以最少、最清晰的代码交付当前所需。

## 📋 终极起飞前核对清单 (The Master Pre-Flight Checklist)

在发起 Pull Request、给版本打 Tag 或宣布完成一项复杂任务前，执行以下四阶段核对：

### 阶段 A：架构与代码品质
- [ ] 每一个模块是否都是深模块（极简接口，内部封装复杂性）？
- [ ] 外部依赖是否封装在适配器后并通过了删除测试？
- [ ] 代码仓库是否保持纯粹无状态（无任何运行日志与状态文件污染）？
- [ ] 代码 Diff 是否外科手术般纯粹，零顺手重构？
- [ ] 命名与代码风格是否严格贴合同一项目的既有规范？

### 阶段 B：验证闭环与安全底线
- [ ] 修 Bug 前是否先编写了稳定复现的红灯测试？
- [ ] 全量单测与代码检查是否 100% 绿灯通过？
- [ ] 是否彻底杜绝了任何危险破坏性的 Git 命令？
- [ ] 输出日志中的所有敏感凭据与 Token 是否已脱敏为 `<REDACTED>`？
- [ ] 生成的模板产物是否已通过无静默崩溃自动化校验？
- [ ] 每条关于渲染布局的结论，是否都能追溯到「已声明视口 + 测量记录」（规则 09）？

### 阶段 C：提示词与受控语言（若涉及 AI 提示词编写）
- [ ] 提示词指令是否符合 ASD-STE100 规范（英文 ≤ 25 词，中文 ≤ 30 汉字，主动语态，无分号）？
- [ ] 静态提示词前缀是否完全冻结以保证最大化命中 Prefix Cache？
- [ ] 解析代码是否对大模型返回的结构做了防御性解包？
- [ ] 关键分类与安全规则是否配备了本地确定性正则/字典硬规则兜底？

### 阶段 D：治理与文档同步
- [ ] PR 描述中是否明确标注了门类型（单向门 vs 双向门）与爆炸半径？
- [ ] PR 是否提供了清晰的改动前后比对证据（Before / After）？
- [ ] 中英文双语文档与使用指南是否在同一个 Commit 中原子级同步？
- [ ] 复杂的架构演进或隐蔽坑点是否已沉淀入经验教训文档？

## 🛑 “拉停生产线”协议 (The Andon Cord Protocol)

当你在开发过程中，或你的 AI 助手在运行期间发现：
1. 需求存在重大未决歧义，无法合理继续；或
2. 既有用例发生意料之外的严重回归；或
3. 即将触犯十大不可触碰红线之一：

**立即拉下虚拟“安灯拉绳 (Andon Cord)”**：
1. **立即中止代码写入**。绝对不要硬着头皮写猜测性代码试图掩盖问题。
2. 整理归纳当前已观测到的核心客观事实。
3. 计算决策前沿，列出权衡分析并附带明确推荐。
4. 提交人类审查者或团队决断后再继续施工。
