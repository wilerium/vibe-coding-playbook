## 🎯 核心问题：“提示词漂移与 Token 浪费”陷阱

在为大模型编写系统提示词（System Prompts）或 Agent 指令时，开发者常常犯下严重错误：
1. **客套虚词与口语废话**：大量填充 *“请你帮我注意...”*、*“在这个任务中你是一个非常棒的助手...”* 等毫无信息量的客套话，不仅白白消耗上下文 Token，还分散了模型的注意力权重。
2. **长难句与分号泛滥**：动辄 50 个词、包含三重从句的复合长句，极易导致注意力机制混淆并引发事实幻觉。
3. **同义词反复横跳导致缓存失效**：在不同提示词中随意变换专业术语（一会儿叫 `issue`，一会儿叫 `defect`，一会儿叫 `bug`），彻底摧毁了大模型服务商的前缀缓存（Prefix Caching）机制。
4. **对结构化输出盲目信任**：天真地以为大模型必定会 100% 遵守 JSON Schema 输出，未在运行时做任何解包容错。

## 📜 规则 3.1：受控技术英语规则（ASD-STE100）
*(思想溯源：ASD-STE100 欧洲航天与防务标准)*

**核心铁律**：所有系统指令、Prompt 模板与高管级摘要，必须严格遵守**简化受控技术英语**。

### 核心约束清单
1. **25 词单句红线**：
   - 英文单句必须控制在 **25 个单词以内**。
   - 凡是超过 25 词的句子，必须拆分为两个独立的原子句。
2. **强制主动语态与动词直达**：
   - **必须**使用主动语态，动作主体明确。
   - 将祈使动词置于句首：`Verify`（验证）、`Extract`（提取）、`Parse`（解析）、`Isolate`（隔离）。
   - **严禁**被动语态（如 `The configuration was modified by the script...`）。
3. **全篇禁用分号 (Semicolon Ban)**：
   - 指令中**绝对禁止使用分号（`;`）**。分号是复合句的温床，直接用句号结束并另起一句。
4. **单句单指令**：
   - 严禁使用 `and`、`while`、`then` 无限串联操作，每句话只阐述一个不可分割的操作指令。
5. **剔除浮夸与营销废话**：
   - **违禁词汇**：`blazing-fast`（极速）、`cutting-edge`（尖端）、`revolutionary`（革命性）、`effortless`（毫不费力）、`smart`（智能）。
   - 直接陈述事实指标：如 `P99 延迟小于 15ms`、`内存占用为 4MB`。

## 📜 规则 3.2：受控技术中文规则 (Controlled Technical Chinese)
*(思想溯源：技术传播学与标准化本地化规范)*

**核心铁律**：输出中文技术文档、工作流指令或摘要时，坚守受控中文标准。

1. **30 字单句上限**：
   - 中文单句长度严控在 **30 个汉字以内**。
2. **直接动作动词（彻底消除名词化虚词）**：
   - **严禁（名词化拖沓）**：`对系统各项配置进行了核查操作`、`实现针对用户数据的抓取工作`。
   - **推荐（动词直达）**：`核查系统配置`、`抓取用户数据`。
3. **标准化状态方括号前缀**：
   - 状态使用标准化方括号强约束：`[处理中]`、`[待集成]`、`[待验证]`、`[已解决]`、`[无法复现]`。
   - 严禁输出含糊其辞的口语表述（如 `大概差不多了`、`还在继续看`）。

## 📜 规则 3.3：确定性前缀缓存优化 (Prompt Cache Optimization)
*(思想溯源：Anthropic & OpenAI Prefix Caching 机制)*

**核心铁律**：从架构层面设计 Prompt，最大化大模型 KV-cache 的复用率。

1. **绝对冻结静态前缀 (Freeze the Prefix)**：
   - 将静态长上下文（系统规则、工具定义、枚举字典、分类学规范）置于 Prompt 的最开端。
   - 保证该前缀在多次调用间**字对字绝对相同**。严禁在前缀中动态插入当前时间戳、随机 UUID 或动态用户名！
2. **动态变量沉底 (Append to Tail)**：
   - 真实变化的用户输入、待分析文本和临时参数，必须严格放置于整个 Prompt 序列的最后部。
3. **消除同义词轮换**：
   - 为系统定义统一的术语词汇表（Glossary）。
   - 统一使用规范术语。如果在某处称之为 `Entity`，全系统绝对不准在其他 Prompt 中写成 `Item`、`Record` 或 `Object`。
4. **经济与性能收益**：
   - 前缀缓存高命中可降低高达 **90%** 的输入 Token 计费，并将首字返回延迟（TTFT）缩减 **80%**。

## 📜 规则 3.4：绝对防御性 AI 设计 (AI Defensiveness)

**核心铁律**：永远将大模型的返回内容视为不受信任的不可靠输入。

1. **防御性多层 JSON 解包**：
   - 大模型极常将 JSON 用 Markdown 代码块包裹（````json ... ````），或者自动包上一层 `{"properties": {...}}` 或 `{"response": {...}}`。
   - 消费代码在进入 Pydantic/Zod 校验前，必须编写专门的解包剥离函数。
2. **关键分类的双重覆盖（确定性硬规则兜底）**：
   - 涉及安全评级、风险判定或核心业务归属时，绝不单凭大模型的语义推断。
   - 必须先运行本地确定性的正则表达式或关键词字典。
   - 一旦触发确定性规则，直接硬性覆盖模型的预测结果。
3. **解析异常的平稳降级 (Graceful Degradation)**：
   - 当大模型输出无法解析或网络超时时，系统必须优雅降级至离线启发式规则，绝对禁止直接抛出未捕获异常导致进程崩溃。

## 🚨 语言与提示词核对清单 (Prompt Checklist)

- [ ] 指令句子是否全部满足上限（英文 ≤ 25 词，中文 ≤ 30 汉字）？
- [ ] 是否彻底消灭了被动语态与营销修饰词？
- [ ] 指令中是否完全禁止了分号（`;`）的使用？
- [ ] 静态 Prompt 前缀是否保持绝对冻结以最大化命中缓存？
- [ ] 动态变量是否完全隔离在 Prompt 最尾部？
- [ ] 核心判定逻辑是否配备了确定性的正则/字典硬规则兜底？
- [ ] 代码是否对大模型返回的嵌套结构进行了防御性解包？
