# 🧩 10. 任务拆解与智能体团队分派

**[English](10_agent_team_decomposition.md)** | **[简体中文](10_agent_team_decomposition.zh.md)**

> *「向进度落后的软件项目加人，只会让它更慢。」* —— 弗雷德里克·布鲁克斯 (Fred Brooks)《人月神话》

---

## 🎯 核心问题：「独狼狂奔」与「表演式团队」

一个能力足够的智能体，如今独自能做的事情很多。这带来两种相反方向的失败，外加三种照旧出错的走法：

1. **独狼狂奔**：一个智能体硬扛一个含两个独立交付物、两个仓库、两套验收标准的请求。上下文在中途耗尽，它只对还记得的那一半报告成功。
2. **表演式团队**：一处单文件修改被拆给五个 teammate。每人重建同一份上下文，Lead 花在仲裁上的时间超过写代码，总墙钟比一个人干还长。
3. **写冲突**：两个「并行」任务写同一个索引文件。第二次写入静默覆盖第一次，直到评审才被发现。
4. **无人见证的完成**：改动的写者自己宣布做完。没有第二个智能体跑过验收命令，于是坏掉的交付物以「已完成」出厂。
5. **弃养的扇出**：任务已分派、最终答复已发出，却还有一个后台作业在跑。它的输出从未进入答复。

**核心要求**：分派是一项可度量的工程决策。只有当并行收益超过协调开销时才拆解；并且每个已分派单元在给出答复前都要收尾。

## 📜 规则 10.1：拆分判定先于动手 (Decomposition Verdict Before Action)

任何需求，在第一次写文件之前，先输出且只输出一行判定。不是一篇计划长文。

```text
拆分判定: 单智能体 | 团队(N 任务) — <理由>
```

**规模门槛**（判定适用于**任何**需求；下列任一条成立即须认真判定，不得以「这个算琐碎」豁免）：
- 预计改动跨越 ≥2 个文件，或 ≥2 个目录；
- 需要 ≥2 条不同的验收命令（或同一命令的 ≥2 次独立运行）；
- 跨越 ≥2 个仓库；
- 交付物里既有写入、又有只读调研。

**要求**：
- 凡跨越一个以上文件、一个以上交付物或一套以上验收标准的请求，动手前必须先出这行判定。
- 判据不成立时必须写 `单智能体`，**不得**为了免责而写 `团队(1 任务)`。判定行是路由，不是护身符。
- 理由里点明决定性的证据：命中的规则 10.2 判据，或使团队不成立的规则 10.3 开销。
- 判定只写一行。它是路由决策，不是设计文档。设计属于任务单。
- 只有在范围发生实质变化时才重新输出判定，并说明变的是什么。

**反模式**：
- 用长篇计划代替判定。计划从不说谁来做。
- 宣布 `团队(4 任务)` 然后自己把四件全干了。此时判定只剩噪音。
- 多交付物请求不出判定，等写到第三个文件才撞上拆分问题。

## 📜 规则 10.2：可并行性判据 (Parallelizability Test)

**核心铁律**：只在工作确实可并行时才组队。数判据，不要凭感觉。

| # | 判据 | 成立的信号 |
| :--- | :--- | :--- |
| a | ≥2 个独立意图或交付物 | 需要两句不同的「做完了」 |
| b | 写范围物理不相交 | 不同仓库、目录或文件集 |
| c | 验收标准不同 | 每个单元需要自己的命令与自己的退出码 |
| d | 有可与写并行推进的只读调研 | 一项不阻塞任何写入的勘查、审计或源码阅读 |
| e | 存在可重叠的长串行工作 | 两条互不占用资源的长串行链 |

**阈值**：至少命中两条判据，**并且**通过规则 10.3 的协调成本闸门，才分派。

**反判据**——命中任一条即强制单智能体。**作用域是单元，不是请求**：

| # | 反判据 | 为什么强制单智能体 |
| :--- | :--- | :--- |
| i | 单一文件单一意图 | 并行收益为零，合并成本不是零 |
| ii | 改动规模小于一个 Agent 回合 | 上下文重建比工作本身还贵 |
| iii | 后一步严格依赖前一步 | 这些单元是一条序列，不是一个团队 |
| iv | 该单元需要再派自己的 teammate | 嵌套分派把协调开销叠成乘积 |

> **`delegate_depth` 这类字段只是自述，不是观测。** 脚本读不到真实的派生行为——teammate 有没有偷偷再派一个，只有判官在规则 10.5 环节核查才能发现。反判据 iv 靠**判官**兜底，不靠 gate。

**优先级仲裁（消除歧义，硬规则）**：
1. **反判据优先于判据。** 同一单元上判据与反判据同时命中时，以反判据为准。
2. **反判据只否掉它命中的那个单元，不否掉整个请求。** 一个请求里两个单元有先后依赖（iii），只把这两个合并成一个单元；其余单元照常并行。**不得**援引 iii 把整个多交付物请求降级为单智能体。
3. 合并后的单元数降到 1，才写 `单智能体`；否则写 `团队(剩余单元数)`。
4. **合并不得跨独立意图。** 两个单元只有在「后一步的输入就是前一步的输出」时才可合并；仅仅"顺路"或"相关"不构成依赖。**独立意图数**是合并后单元数的下界——原始有几个互不产出的交付物，合并后至少还剩几个单元。

**要求**：
- 按实际工作评估判据，不按请求的措辞评估。一段话里仍可能装着三个独立交付物。
- 在判定理由里写明命中条数，例如 `团队(3 任务) — 判据 a、b、c`。
- 把写并行推进的调研当作一等判据。一项能解开后续决策的只读勘查就是并行工作。

**反模式**：
- 把「用户说要组队」当判据。意图不是判据。
- 因为碰的是不同文件就称串行步骤为并行。依赖顺序会击穿不相交。
- 按请求的段落拆，而不是按交付物拆。

## 📜 规则 10.3：协调成本闸门 (Coordination Cost Gate)

**核心铁律**：分派有固定开销。省下的时间小于该开销时，自己做。

| 固定开销 | 谁付 | 典型形态 |
| :--- | :--- | :--- |
| 上下文重建 | 每个 teammate | 重读 Lead 已经读过的源 |
| 写范围仲裁 | Lead | 决定谁拥有哪个文件，然后盯住 |
| 汇总与复核 | Lead | 收集报告、跑验收命令、对账 |
| 集成 | Lead | 合并在运行中各自漂移的单元 |

**要求**：
- 分派前估算省下的墙钟与开销。余量很薄时，用一句话把两个数都写出来。
- 点名你预期的那笔开销。说不出来就管不住它。
- 两个数接近时选单智能体。平局归更便宜的那侧。
- 绝不为「看起来专业」而组队。一个跑完的单人胜过一支在协调的队伍。

**反模式**：
- 把单文件修改分派出去。
- 扇出一个本来就装得下一个 Agent 回合的任务。
- 拆完工作，再自己逐个重读单元来对账。同一笔开销付了两次。

## 📜 规则 10.4：写范围不相交 (Disjoint Write Scopes)

**核心铁律**：每张任务单都声明 write_scopes。重叠只是告警不是锁，所以 Lead 必须物理切分工作。

**要求**：
- 在任何 teammate 动手之前，把 write_scopes 以路径前缀的形式写到任务单上。
- 同一文件同一时刻只有一个写者。一个文件两个写者，意味着其中一个会丢。
- 把共享索引文件、变更日志与依赖清单当作单主区域。指派给一个写者，或把碰它的任务串行化。
- 两个单元必须碰同一文件时，用显式依赖排序，等第一个完成后合并第二个。
- 同伴可能在你上次读取之后写过该文件时，先重读再写。

**机械校验（不靠自觉）**：把任务单集合交给一个 gate 脚本，让「能不能这样拆」变成退出码。
接口约定：脚本读任务单数组（每张含 `write_scopes` / `acceptance` / `owner` / `verifier`），并可接收判定行字符串；退出码 `0`=合法可下发 / `2`=命中违规 / `3`=字段不全或脚本异常（**fail-closed**）。
与规则 6.5 的提交门禁脚本同构——**没有 gate 的闸门只是荣誉制**。

gate 应尽力覆盖**两端**，但两端的覆盖强度**不对等**，必须说清：
- **下游「拆得对不对」（强）**：写范围两两重叠（`realpath` + 大小写折叠归一后比较）、`owner != verifier`、`acceptance` 非空话、嵌套分派。
- **上游「该不该拆」（弱，只有三个机械信号）**：
  1. 任一任务单跨越 ≥2 个顶层区域 → 报警（独狼的机械信号，阈值与判据 a/b 对齐）；
  2. 判定行声明的任务数与实际任务单张数不一致 → 报警；
  3. 若 gate 被授予读取版本控制实际改动（`git diff` 之类）的能力，则把实测改动与任务单自报的 `write_scopes` 做**覆盖测试**，未覆盖的改动列为审计提示；**默认不阻断**（工作树常含他人残留改动，恒定阻断会训练人绕过闸门），仅在显式严格模式下阻断。读取源不可用时必须 **fail-closed**，不得静默跳过。
- **上游仍漏网的情形，必须承认**：执行者从一开始就写「这是单智能体」并且只建一张单、写范围也写成单一区域——gate **没有任何东西可以反驳**，因为此时它手上只有执行者自己给出的全部输入。**这一层只能靠规则 10.5 的独立判官兜底，不能宣称已被机械拦住。**

**gate 不能替代人的判断**：它只能从「已交出的任务单」里读信号，读不出你没写下来的想法。判定行本身仍由执行者给出——gate 只校验它与实际单子是否自洽。**先判定，再建单，再 gate。**

**反模式**：
- 假定工具会阻止冲突。它只报告，不阻止。
- 两个任务都改同一个 README 却声明独立。
- 两个单元都写完了才发现重叠。此时第二次写入已经是一次静默回滚。

## 📜 规则 10.5：判官独立 (Independent Verdict)

**核心铁律**：写者绝不宣布完成。判定由另一个智能体给出，并附可执行命令的原始输出。

**要求**：
- 把验收命令挂到任务单上。评审者无法执行的验收标准，不算验收标准。
- 判定必须落在 `PASS`、`FAIL`、`BLOCKED`、`NOT DELIVERED` 之一，并附命令的原始输出与退出码。
- 判官自己跑命令。只读写者摘要的判官什么也没验证。
- 让判官的上下文与写者的上下文保持分离。独立性是运行的属性，不是头衔的属性。
- 没有第二个智能体可用时，照样附原始输出，但把结论收成 `BLOCKED — unverified`。绝不标 `PASS`。

**反模式**：
- 「做完了」却不给退出码。
- 判官重读 diff 然后表示赞同。
- 写者与判官是同一个上下文，只换了标签。

## 📜 规则 10.6：汇总与回收 (Harvest and Close)

**核心铁律**：直到每个已分派单元都回报、每个后台作业都被收齐或取消，工作才算结束。

**要求**：
- 给最终答复之前，列出为本次请求启动的所有 teammate 与所有后台作业。
- 收齐每个仍有意义作业的输出。取消已无关的作业，并说明你取消了它们。
- 每张任务单必须有明确结论：`PASS`、`FAIL`、`BLOCKED` 或 `NOT DELIVERED`。挂着不结不是结论。
- 把失败与阻塞的单元写进答复。静默丢掉的单元会被读成成功。
- 等待或超时之后重新列一遍单元。超时不是结果。

**反模式**：
- 作业还在跑就把最终答复发出去。
- 因为工作「差不多」落地了，就把任务单留在进行中。
- 只报通过的三张单，略过失败的那一张。

## 📜 规则 10.7：反模式清单 (Anti-Patterns)

**核心铁律**：先命名失败形态，再命名替代做法。一条只禁止不给出口的分派规则不可用。

| 反模式 | 症状 | 正确做法 |
| :--- | :--- | :--- |
| 一个文件的委员会 | 三个智能体、一个文件、一个意图 | 单智能体（规则 10.2 反判据 i） |
| 无汇总的扇出 | 单元已分派、答复已发出、作业成孤儿 | 先按规则 10.6 汇总 |
| 「并行」任务却写同一文件 | 第二次写入静默回滚第一次 | 按规则 10.4 切分写范围 |
| 为逃避阅读而分派 | 让 teammate 去总结 Lead 从未打开的源 | 先自己读，再决定（规则 10.3：上下文重建由谁付） |
| 派了人自己又重做一遍 | Lead 分派后又把该单元重做 | 只留一个主人，让判定收尾（规则 10.5） |
| 把分派当进度 | 用团队规模汇报进展 | 套用规则 10.3 的成本闸门 |
| 无界层级 | teammate 再派自己的 teammate | 每个请求只允许一层分派（规则 10.2 反判据 iv） |
| 无验收的任务单 | 把「优化一下」当工作派出去 | 按规则 10.5 给可执行命令 |

**要求**：
- **本表每一行都是约束条款，不只是举例。** 表内已在括号里注明对应条款编号的行，其约束力来自该条款；未注明的行由本规则 10.7 直接约束。
- 在自己的运行里撞上其中一行时，指出是哪一行，并在同一轮内纠正。
- 优先选仍然装得下独立判定的最小单元。

**反模式**：
- 命名了反模式却不改方案。
- 每出一次事故就加一条新规则。应该扩展这张表。

## 🤖 给 AI Agent 的提示词模板

**T1 — 动手前先判定**

> 在编辑任何东西之前，先输出一行：`拆分判定: 单智能体 | 团队(N 任务) — 理由`。理由必须点名命中的规则 10.2 判据，或使团队不成立的规则 10.3 开销。不要写计划代替它。

**T2 — 写任务单**

> 每个单元写一张任务单。包含目标、以路径前缀表示的 write_scopes、验收命令及其期望退出码，以及与其它任务单的依赖顺序。若两张单共享同一路径前缀，先合并或先串行化再分派。

**T3 — 答复前先汇总**

> 列出为本次请求启动的所有 teammate 与后台作业。逐个报告状态、验收命令的原始输出，以及 PASS、FAIL、BLOCKED、NOT DELIVERED 之一。取消不再需要的作业。这张表不完整就不要答复。

**T4 — 每条分派的守门条款**

> 写者不得宣布完成。判定必须附命令与原始输出。同一文件不得同时有两个写者。任何单元不得无结论被丢弃。任何分派不得缺少被点名的协调开销。

## 🚨 团队分派核对清单

- [ ] 第一次写入之前是否已有单行拆分判定？
- [ ] 是否按规则 10.1 的规模门槛判定，而不是口头声称「这个算琐碎」？
- [ ] 判定是否点名了命中的判据或被排除的开销？
- [ ] 是否至少命中两条可并行性判据，并通过成本闸门？
- [ ] 反判据是否只否掉它命中的单元，而没有把整个请求降级为单智能体？
- [ ] 是否没有嵌套分派（teammate 不得再派 teammate）？
- [ ] 每张任务单是否以路径前缀声明 write_scopes？
- [ ] 每个文件在同一时刻是否只有一个写者？
- [ ] 共享索引文件、变更日志与清单是否单主或已串行化？
- [ ] 每张任务单是否带可执行验收命令？
- [ ] 判定是否由独立智能体给出，并附原始输出与退出码？
- [ ] 答复之前每个 teammate 与后台作业是否已收齐或取消？
- [ ] 每张任务单是否落在 PASS、FAIL、BLOCKED 或 NOT DELIVERED？

## ⚖️ 与规则 01、06、07 的边界

- **规则 01（认知纪律）**决定*是否*向人类提问以及推荐什么。规则 10 决定已批准的工作*由谁*执行。
- **规则 06（研发治理）**判定可逆性、爆炸半径与审查轴。规则 10 消费该判定：单向门留在 Lead 手里，双向门可以分派。
- **规则 07（总清单）**负责发布红线。其现有十条红线**尚不覆盖分派**；规则 10 独立约束分派，并建议规则 07 在下次修订时吸收一条：「没有独立判定与汇总，不得分派」。
