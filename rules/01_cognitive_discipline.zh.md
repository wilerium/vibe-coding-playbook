# 🧠 01. 认知决策与决策前沿 (Cognitive Discipline & Decision Frontiers)

**[English](01_cognitive_discipline.md)** | **[简体中文](01_cognitive_discipline.zh.md)**

> *“最初 90% 的代码用去了 90% 的开发时间。剩下的 10% 的代码又用去了剩下的 90% 的开发时间。”* — 汤姆·卡吉尔 (Tom Cargill)

---

## 🎯 核心问题：“心流编码”陷阱 (The Vibe Coding Trap)

当开发者或自主 AI Agent 以极快对话速度编码时，极易陷入以下破坏性陷阱：
1. **静默盲猜 (Silent Guesswork)**：遇到模糊需求时，Agent 悄悄自行假定一种技术实现，编写了上百行代码，直到用户测试时才暴露方向错误。
2. **多轮碎片化逼问 (Scattered Questions)**：在多轮对话中零敲碎打地发问，打断人类注意力并拖慢推进节奏。
3. **Diff 严重污染 (Diff Pollution)**：在修复一个 2 行的小 Bug 时，Agent “顺手”把整个文件的格式、空白、未用 import 全清理了一遍，导致审查无法聚焦。
4. **提前过度设计 (Premature Over-Engineering)**：为从未被要求的未来场景设计了复杂的抽象基类、泛型工厂类和各种冗余配置开关。

## 📜 规则 1.1：先思考后编码（决策前沿逼问机制）
*(思想溯源：Andrej Karpathy & Matt Pocock `grilling`)*

**核心铁律**：面对具有多种可行架构或存在业务歧义的需求时，**绝对禁止静默选择一条路径并继续编写代码**。

### 决策前沿协议规范 (Decision Frontier Protocol)
在动笔编写任何业务代码前，必须执行以下步骤：
1. **先查事实 (Facts First)**：
   - 先行检索本地代码、配置文件与既有用例。**严禁询问用户已经在代码库中写明的事实**。
2. **计算决策前沿 (Decision Frontier)**：
   - 决策前沿指决策树中当前尚未决断、且其前置假设已满足的分支集合。
   - **绝对不要**询问那些依赖于前置未定决断的深层问题。
3. **单轮打包提问（最多 4 个问题）**：
   - 将当前决策前沿的所有关键架构决断打包至**单一轮次**中。
   - 每个问题提供清晰的编号选项。
4. **强制附带推荐方案**：
   - 每一个问题必须明确附带推荐标注：
     `➡️ **建议方案**: [选项 X] (推荐)`
   - 用一句话讲透权衡理由（Trade-off）。
5. **一键确认标准 (The One-Word "Yes" Standard)**：
   - 提问结构必须支持人类直接回复 `"Yes"`、`"好"` 或 `"按推荐执行"`，即可一键批准整套方案开始施工。

### 错误范例 vs 最佳实践
```markdown
❌ 错误反例（静默下注）：
用户："给用户查询接口加个缓存。"
Agent：（一声不吭直接引入并配置了 Redis，哪怕当前项目其他地方全是纯内存或 SQLite 缓存。）

✅ 最佳实践（决策前沿逼问）：
Agent："已分析查询接口与数据特征。在实现缓存前，以下是核心决策前沿：

1. 缓存存储选型：
   [1] 进程内内存 LRU 缓存（零外部依赖，极快，适合单节点服务）(推荐)
   [2] 本地 SQLite 文件缓存（支持重启持久化，零网络开销）
   [3] 独立 Redis 实例（支持分布式共享，但需要额外基础设施依赖）
   ➡️ **建议方案**: [1] 进程内 LRU 缓存，当前系统为单节点部署，无需引入额外中间件负担。

回复 'Yes' 即刻按建议方案开工，或指出您的偏好选项。"
```

## 📜 规则 1.2：极简主义（奥卡姆剃刀法则）
*(思想溯源：Andrej Karpathy)*

**核心铁律**：用最少、最清晰的代码解决眼前问题。严禁任何预测性的灵活性设计。

1. **拒绝投机性泛型与工厂**：
   - 绝不为单次业务场景编写泛型抽象基类或工厂模式。
   - 始终先写具体代码；只有在第 3 个具体的复用场景出现时（三次原则，Rule of Three），才考虑提取抽象。
2. **拒绝未要求的主动加配置**：
   - 默认采用合理的硬编码默认值，除非用户明确要求动态配置。
   - 严禁“防患于未然”式地添加无用的 CLI 开关、环境变量或配置字段。
3. **50 行 vs 200 行的灵魂拷问**：
   - 在呈现代码前自问：*“一位资深主任工程师看到这段代码，会不会觉得写得太重、太复杂了？”*
   - 如果 50 行干净代码能解决，写出 200 行就是典型的劣质工程交付。

## 📜 规则 1.3：外科手术式修改（保持 Diff 极度纯净）
*(思想溯源：Andrej Karpathy)*

**核心铁律**：只触碰必须修改的代码；只清理自己产生的垃圾。

1. **Diff 可追溯性检验**：
   - `git diff` 中的每一行变动，都必须能够直接对应到用户当下的需求或 Bug 现象。
2. **杜绝“顺手重构” (No Drive-By Refactoring)**：
   - **绝对禁止**：在修 Bug 或写新功能时，顺便把周围无关代码的缩进修一下、import 排个序、旧注释改改错字。
   - 哪怕周围的代码看起来非常丑陋，只要与当前任务无关就必须保持原样不动。顺手修改会淹没真正关键的审查 Diff，并带来历史隐蔽契约断裂的风险。
3. **完全模仿既有规范**：
   - 严格贴合代码库中已有的命名习惯、缩进和目录规范，即便它不符合你个人的审美偏好。
4. **及时清理自己留下的痕迹**：
   - 开发完成后必须主动删除所有临时的调试打印、日志埋点、探索性脚本以及无用引用。

## 📜 规则 1.4：目标驱动执行与微验证计划
*(思想溯源：Kent Beck)*

**核心铁律**：将模糊的祈使句指令转化为具有明确通过标准的验证目标。

1. **先定验证手段，再写实现代码**：
   - 将 *“增加邮箱格式校验”* 转化为：
     - `[步骤 1]` 编写针对非法邮箱的测试用例 -> 验证: 测试失败（红灯）。
     - `[步骤 2]` 编写邮箱校验核心正则 -> 验证: 测试通过（绿灯）。
     - `[步骤 3]` 运行既有用例 -> 验证: 0 回归。
2. **多步骤微验证计划**：
   - 针对 3 步以上的非简单任务，必须先输出微验证计划：
     ```text
     [步骤 1: 脚手架搭建] -> 验证: 文件存在并导出预期接口
     [步骤 2: 核心业务编写] -> 验证: 单元测试全部绿灯
     [步骤 3: 终端集成]   -> 验证: CLI 命令返回状态码 0
     ```

## 🚨 认知决策核对清单 (Cognitive Checklist)

- [ ] 在面临非显然的架构选型时，是否先计算了决策前沿？
- [ ] 提问是否在单轮内打包完毕并提供了明确的推荐项？
- [ ] 代码 Diff 中的每一行变动，是否都能溯源至用户需求？
- [ ] 是否彻底杜绝了顺手重构、格式化周围无关代码的行为？
- [ ] 是否以最精炼的代码解决问题，无任何过度前瞻性设计？
- [ ] 是否在任务结束前彻底清理了所有调试脚本和临时产物？
