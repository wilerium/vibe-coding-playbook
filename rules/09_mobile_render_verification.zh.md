# 📱 09. 移动端与渲染界面验证

**[English](09_mobile_render_verification.md)** | **[简体中文](09_mobile_render_verification.zh.md)**

> *「程序测试可以证明缺陷存在，但永远不能证明缺陷不存在。」* —— Edsger W. Dijkstra

---

## 🎯 核心问题：「我这儿看着没问题」

渲染界面失败的方式和逻辑缺陷不同。脚本退出码 `0`、静态检查通过、HTML 结构合法——但在目标设备上布局就是错的。四种失败模式最常见：

1. **退出码乐观**：构建脚本或静态审计通过，Agent 就宣布完成。静态分析读的是文本，看不见几何。
2. **肉眼认证**：人或视觉模型看一眼截图说「挺好」。这个结论不可复现、不可 diff、无法写进评审门槛。
3. **假定的工具链**：验证脚本引用的模拟器程序、设备名或 URL 协议早已不存在，或本来就不兼容。脚本「跑完了」，却什么也没验证。
4. **未声明的视口**：「一屏放得下」在声明视口之前毫无意义——浏览器工具栏、安全区、缩放倍率都会改变结论。

**核心要求**：关于布局的结论，只有在**真实渲染**中、对照**已声明的视口**、并以**机器可复核的数字**表达时才成立。

---

## 📜 规则 9.1：渲染即事实

对渲染界面，静态检查与单元测试是必要条件，永远不是充分条件。

| 检查类型 | 能证明 | 不能证明 |
| :--- | :--- | :--- |
| 退出码 / 单元测试 | 逻辑与数据流 | 任何像素相关的事 |
| 静态结构审计 | 结构、锚点、无外链 | 溢出、换行、截断、点击目标尺寸 |
| 人工看截图 | 主观印象 | 可复现性、回归 |
| **渲染 + 实测** | 已声明的几何约束 | 视觉品味 |

**要求**：
- 明确说明你验证的是哪一层。「静态审计通过」是成立的表述；「布局正确」在没有实测前不成立。
- 需求一旦是几何性的（一屏放下、无横向滚动、标签不被截断），就必须写成数值断言，而不是描述。

---

## 📜 规则 9.2：先声明视口契约

测量之前，先把契约写下来。

```text
基准视口（REFERENCE VIEWPORT）
  设备型号     : <如 iPhone 18 Pro Max>
  逻辑尺寸     : <宽> x <高> 点
  原生像素     : <宽> x <高> @ <倍率>x
  浏览器外壳   : 无 | 浏览器工具栏 | 应用导航栏
  安全区       : 顶部 <n> / 底部 <m> 点
```

三个直接后果：

1. **必须断言渲染器回报的视口就是这个值。**实测 `innerWidth` 与契约不符时，后续所有结论都是假的，要立刻失败。
2. **每条结论都要注明渲染面。**「浏览器外壳下放得下」和「整屏放得下」是两个不同命题，不能混在同一份报告里。
3. **每个需求定一台基准设备。**矩阵里最宽的那台永远暴露不出窄屏回归。主判据一台，另配至少一台更窄的回归机型。

**反模式**：用当前恰好启动的那台设备测量，然后把结果当成普适结论。

---

## 📜 规则 9.3：输出测量值，不输出形容词

每次渲染检查都要为**每页、每设备**产出一条机读记录。人看截图，Agent 必须读数字。

```json
{
  "page": "<路由标识>",
  "device": "<设备型号>",
  "innerWidth": 440, "innerHeight": 956,
  "safeTop": 62, "safeBottom": 34,
  "usableHeight": 860,
  "scrollWidth": 440, "scrollHeight": 984,
  "fitsFull": false, "fitsUsable": false,
  "hOverflow": false, "overflowEls": [],
  "viewportFitCover": true
}
```

记录规则：
- **每页每设备一行**，禁止用聚合值掩盖哪一页失败。
- **布尔值由计算得出，不由判断得出。**`fitsFull` 是 `scrollHeight <= innerHeight`，由检查器算，不是 Agent 断言。
- **溢出时附元素清单。**`overflowEls` 把「有个东西太宽」变成可定位的修复点。
- **记录写在代码仓库之外**（数据根或构建目录），并保证跨轮次可 diff。

---

## 📜 规则 9.4：区分两个渲染面

移动端 Web 界面有两个渲染面，看起来一样，量出来不一样：

| 渲染面 | 视口 | 用途 |
| :--- | :--- | :--- |
| 浏览器内 | 被工具栏与外壳吃掉一截 | 真实首次打开观感 |
| 全屏宿主（独立应用 / 添加到主屏幕） | 整屏，安全区交给 CSS | 几何判定、「一屏」结论 |

**要求**：
- 几何需求**只在全屏渲染面**判定。
- 首屏观感可以在浏览器面检查，但必须标注是哪一面。
- 若页面未声明安全区布局（`viewport-fit=cover` 加 `env(safe-area-inset-*)` 内边距），全屏渲染会把内容压到状态栏下面。要检测出来（`viewportFitCover: false`）并报告，不得让与系统 UI 冲突的布局静默上线。

**实现提示**：一个极简的 WebView 宿主应用就够了。几十行代码，用平台自带工具链编译，既能得到确定性的全屏渲染，又能脚本化读取渲染后的文档。不要靠缩放桌面浏览器窗口来模拟移动视口。

## 📜 规则 9.5：传输方式本身就是被测对象

本地产物不会自动被目标渲染器访问到。

- 用 `file://` 打开本地文件，可能被文件提供者或文档选择器接管，而不会进入浏览器。此时截图得到的是文件浏览器，不是页面。
- 本地产物用**临时回环 HTTP 服务**提供：绑定 `127.0.0.1`、端口 `0`（内核分配）、只读处理器、不打访问日志、跑完即关。
- **不要假定路由行为能跨传输方式沿用。**基于 hash 的导航、历史记录、fetch 限制在 `file://` 与 `http://` 下可能不同。
- 先验证传输，再验证内容。首次渲染是空白或弹出选择器时，先修传输——不要对着一个从未加载的页面调 CSS。

## 📜 规则 9.6：夹具幂等，失败要诚实

验证夹具的腐化速度比产品代码快。默认所有标识符都是错的，直到你探测过。

1. **探测，不要硬编码。**设备名、运行时标识符、二进制路径都会随工具链版本变化。运行时查询，从实际存在的集合里选。
2. **先复用，再创建。**模拟器与容器的创建接口常常允许重名。先查已有夹具；盲目创建会每跑一次留下一台孤儿，结果也变得含混。匹配时要同时比对**名称与夹具类型**。
3. **兼容性不等于版本顺序。**最新运行时不一定能承载目标设备。查运行时的受支持设备清单，选**最新且兼容**的那个；并把跳过哪些运行时、为什么跳过打印出来。
4. **等稳定，不要等时长。**固定 sleep 会和渲染器赛跑。反复采样直到连续两次截图完全一致，并设重试上限。
5. **检测「盲态」。**连续两页截图字节完全相同，说明导航根本没发生。判为失败，绝不判为通过。
6. **失败关闭（fail closed）。**缺少测量就是失败。「没有数据」永远不能报成功，退出码必须体现这一点。

---

## 📜 规则 9.7：给验证分层，别让快循环变慢

便宜的快循环保持快，昂贵的矩阵留给交付。

| 层级 | 耗时 | 内容 | 时机 |
| :--- | :--- | :--- | :--- |
| L0 静态 | 秒级 | 结构审计、死锚点、外部引用 | 每次编辑 |
| L1 单机渲染 | ~10 秒 | 主判据设备、受影响的页面子集、测量值 | 每次 UI 改动 |
| L2 全矩阵 | 分钟级 | 全页面、主判据加窄屏回归设备 | 合并前 |
| L3 双渲染面 | 分钟级 | L2 在浏览器面与全屏面各跑一遍 | 发布前 |

**契约**：每一层都是**一条命令 + 有意义的退出码**，可直接写进任务单的验收行。评审者无法执行的验收标准，不算验收标准。

## 🤖 给 AI Agent 的提示词模板

**T1 — UI 改动后自检**

> 在主判据设备上对你改过的页面跑渲染检查。把每页的 `scrollHeight` 与 `hOverflow` 和上一轮对比，只报告哪几页变了、变化多少点。不要用「看起来正确」描述截图。

**T2 — 交付前验收**

> 跑全量渲染验证并开启一屏断言。退出码非 0 时，逐条原样粘贴「内容高 N > 视口 M（超出 X 点）」，然后为每个超标页给出最小 CSS 改动方案。没有退出码不得汇报任务完成。

**T3 — 排查用户反馈的布局问题**

> 先探测环境（设备清单、运行时兼容性、页面数量）。然后只渲染出问题的那一页，报告实测视口、内容高、溢出元素。判断根因是传输、视口契约还是 CSS。不要猜。

**T4 — 视觉回归扫描**

> 对比两次运行的测量记录。列出 `scrollHeight` 变化超过 8 点的页面，按变化幅度排序，并结合本次改动说明标注每一处是预期还是意外。

**T5 — 每个 UI 任务的守门条款**

> 不得仅凭截图认定布局合格。不得用 file 协议打开本地产物。不得引用本环境中未经探测的工具名或设备标识符。完成必须有测量记录或通过的退出码支撑。

## 🚨 渲染界面验证清单

- [ ] 基准视口是否已声明（设备、逻辑尺寸、倍率、外壳、安全区）？
- [ ] 渲染器回报的视口是否与该值完全一致？
- [ ] 每条几何需求是否都写成了带退出码的数值断言？
- [ ] 测量记录是否按「每页每设备」落盘、且在代码仓库之外？
- [ ] 是否先验证传输再验证内容（回环 HTTP，不依赖 file 协议）？
- [ ] 夹具是否先探测、复用、清理，而不是盲目创建？
- [ ] 是否检查了运行时与目标设备的兼容性？
- [ ] 连续两次完全相同的截图是否判为失败？
- [ ] 缺失测量时是否失败关闭，而不是静默通过？
- [ ] 除主判据外，是否至少有一台更窄的回归设备？

## ⚖️ 与规则 04、05、07 的边界

- **规则 04（UI/UX）**定义好的布局**是什么**；规则 09 定义如何**证明它真的渲染出来了**。
- **规则 05（取证式调试）**负责逻辑缺陷的红灯循环；规则 09 提供渲染侧的对应物：先测量，再动手改。
- **规则 07（总清单）**负责发布红线。规则 09 为它贡献一条：没有测量记录，不得声称布局合格。
