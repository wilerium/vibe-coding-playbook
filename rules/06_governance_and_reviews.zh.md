# ⚖️ 06. 研发治理、双轨审查与工程寻路 (Governance, Reviews & Wayfinding)

**[English](06_governance_and_reviews.md)** | **[简体中文](06_governance_and_reviews.zh.md)**

> *“你不可能通过事后检验把质量塞进产品里，质量必须从一开始就被设计与构建进去。”* — 戴明 (W. Edwards Deming)

---

## 🎯 核心问题：“决策迷雾与混乱的 PR”陷阱

在快节奏、跨多会话的软件工程迭代中，研发流程极易滑向失控：
1. **运维风险不透明**：提交 PR 时未声明改动是轻量可逆的，还是涉及不可逆的数据模式迁移，导致审查者无法精准分配精力。
2. **代码审查两套标准混淆**：审查者把“代码规范检查”（格式、缩进、无状态、无泄露）与“业务需求核对”（边界测试、功能契约）混为一谈，导致审查流于表面。
3. **跨期任务决策迷雾**：大型工程在多轮会话中迷失，原因在于工程师在底层架构依赖尚未确立前，就盲目开始编写上层业务代码。
4. **多语言文档不同步 (Documentation Drift)**：代码改了，但使用指南、API 文档以及中英文双语翻译严重滞后，造成长期的知识债务。

## 📜 规则 6.1：单向门与双向门决策模型 (Door Types & Blast Radius)
*(思想溯源：Jeff Bezos 亚马逊股东信决策方法论)*

**核心铁律**：每一个架构提案与 Pull Request，必须显式分类其**门类型 (Door Type)** 与**爆炸半径 (Blast Radius)**。

### 1. 门类型判定 (Door Type)
* **双向门 (Two-way Door，高度可逆)**：
  - 能够以极快速度完成回滚，且绝对不会引起持久化数据污染或服务中断的改动。
  - *范例*：纯前端 CSS 样式微调、内部帮助函数重构、新增单元测试、业务纯逻辑算法优化。
  - *应对策略*：快速试错，轻量化审查，鼓励果断推行。
* **单向门 (One-way Door，极难逆转)**：
  - 涉及数据库表结构变更、基线快照重写、公共 API 签名修改或调用第三方写接口产生外部副作用的改动。
  - *应对策略*：严谨推演，强制进行架构预审，制定详细的事故回滚计划（Rollback Plan）。

### 2. 爆炸半径评估 (Blast Radius)
* **单点隔离 (Isolated)**：仅影响单个轻量脚本、单测或独立小组件。
* **模块管道 (Pipeline-Wide / Subsystem)**：影响整个业务子系统、某条特定批处理流水线或核心数据流。
* **全局核心 (Global)**：波及底层共享引擎、数据库连接基座、CLI 顶层调度器或认证鉴权中间件。

## 📜 规则 6.2：结构化 Pull Request 审查模板

**核心铁律**：标准化所有 PR 描述，强制提供前后比对证据与风险声明。

```markdown
## 变更概括 (Summary)
<简要描述本次改动、架构演进思路或调用拓扑图>

## 验证证据 (Evidence)
- **改动前 (Before):** <基线截图 / 失败的报错日志 / 红色测试输出>
- **改动后 (After):**  <修改后界面截图 / 绿灯通过的测试输出 / 验证成功的命令行输出>

## 危险度与爆炸半径 (Merge Danger & Blast Radius)
- **门类型 (Door Type)**: `双向门 (Two-way Door)` (可逆) OR `单向门 (One-way Door)` (不可逆数据/状态迁移)
- **爆炸半径 (Blast Radius)**: `单点隔离 (Isolated)` | `模块管道 (Subsystem)` | `全局核心 (Global)`
- **回滚预案 (Rollback Plan)**: <若上线后发生异常，确切的一键回退步骤>

## 知识回流沉淀 (Knowledge Integration)
- **教训沉淀 (Lessons Learned)**: <本次是否解决了隐蔽坑点？是否已沉淀入经验手册？>
- **双语同步 (Documentation Sync)**: <用户手册与中英文双语文档是否已原子级同步？>
```

## 📜 规则 6.3：双轨代码审查机制 (Two-Axis Code Review)
*(思想溯源：Matt Pocock `code-review`)*

**核心铁律**：将代码审查拆解为正交独立的**规范轴**与**需求轴**，分别评估与打分。

```
                         ▲ 轴 2：功能需求契约 (Functional Spec)
                         │
     "技术规范写得很好， │  🎯 理想的合入标准 (IDEAL PR)
      但业务逻辑理解偏了"│  (双轴均获得高分，且有
                         │   充分的验证证据)
                         │
  ───────────────────────┼────────────────────────► 轴 1：工程规范与安全
                         │                          (外科手术式修改、深模块、
     ❌ 坚决打回         │  "功能确实实现了，
     (两轴均不及格)      │   但代码极脏、存在安全漏洞、
                         │   严重污染代码库"
```

### 轴 1：工程规范与安全标准 (Engineering Standards)
- **外科手术式 Diff**：是否存在顺手重构无关代码或批量格式化？
- **数据隔离**：仓库是否保持绝对无状态？有无相对路径硬编码？
- **语言与类型**：类型系统是否健全？提示词是否遵循受控语言？
- **接缝与解耦**：外部依赖是否封在适配器中？是否通过删除测试？

### 轴 2：功能需求契约 (Functional Specification)
- **需求保真度**：是否 100% 达成了用户的预期目标？
- **边界与异常用例**：是否覆盖了空指针、超时、空数组等边界条件？
- **杜绝多余蔓延**：是否克制地只做所要求的事，无任何预测性过度设计？

## 📜 规则 6.4：大型跨会话工程寻路 (Initiative Wayfinding)
*(思想溯源：Matt Pocock `wayfinder`)*

**核心铁律**：对于跨越多轮会话或多 PR 的大型工程，先绘制**有向无环图 (DAG) 决策工单**，严禁在架构未明朗时仓促开工。

```text
决策工单 DAG 范例：
[工单 1: 核心领域实体契约设计] ──► [工单 2: 存储适配器抽象接口]
                                              │
                                              ▼
[工单 3: 内存缓存具体实现]     ◄─── [工单 4: 数据库驱动适配器]
              │
              ▼
[工单 5: REST API / CLI 终端接入]
```

### 寻路三大法门
1. **决策工单前置于编码工单**：
   - 优先敲定具有前置依赖关系的架构决断。
   - 底层数据契约未敲定前，绝不开工下游展示模块。
2. **上下文零依赖独立性**：
   - DAG 中的每个工单必须足够自包含，即使换由一个全新会话接手，也能无需上文直接开工。
3. **原子级独立验证**：
   - 每个决策工单落地时必须配备独立的自动化验证卡点。

## 📜 规则 6.5：文档孪生绝对同步纪律 (Bilingual Twin Rule)

**核心铁律**：对用户手册、API 规范或架构说明的任何改动，必须在**同一个原子 Commit** 中同步更新中英文双语版本（`*.md` 与 `*.zh.md`）。

* 严禁单语种滞后更新，滞后就是事实上的文档腐烂。
* 在自动化流水线或提交门禁中，强制校验双语文件的一致性。

## 🚨 研发治理核对清单 (Governance Checklist)

- [ ] PR 是否明确声明了门类型（单向门 vs 双向门）与爆炸半径？
- [ ] PR 描述中是否提供了详实的改动前后对比证据（Before / After）？
- [ ] 代码审查是否分别在规范轴与需求轴上完成了独立检验？
- [ ] 大型工程是否在动手前拆解为 DAG 决策工单图？
- [ ] 中英文双语文档是否在同一个 Commit 中原子级完成同步？
- [ ] 针对单向门等高危操作，是否制定了清晰可行的回滚预案？

## 📜 规则 6.5：提交门禁判定（Commit Gate）—— 什么能直推，什么必须开 PR

*(本规则为「无论哪个 AI、哪个模型都能机械执行」而写：判据全部是可数事实，不依赖主观判断。)*

**核心铁律**：**默认走 PR。** 直推 `main` 是**例外**，必须逐条满足下面的「直推白名单」；**只要触线一条，就开 PR**。

### 1. 判据表（命中任意一条 → 必须开 PR）

| # | 判据 | 为什么 |
| :--- | :--- | :--- |
| G1 | 改动**跨越 ≥3 个功能域**（如：渲染器 + 生成脚本 + 文档 + 工具链） | 多个意图混在一个 diff 里，审不出来 |
| G2 | 新增/删除 **≥400 行**（不含测试与生成物） | 大 diff 实质等于「不审」 |
| G3 | 触及**公共接口签名**（函数参数、返回结构、路由、CLI 参数、配置键） | 破坏性变更需要人确认 |
| G4 | 触及**数据格式 / 序列化 / 存储布局** | 回滚代价高（数据污染） |
| G5 | 触及**鉴权、凭据、路径解析、文件写入位置** | 安全面 |
| G6 | 引入**新依赖**（pip/npm/brew/system） | 影响可重建性与供应链 |
| G7 | 触及**发布物**（版本号、构建脚本、镜像、发布配置） | 影响下游 |
| G8 | 引入**外部素材或第三方内容**（图片、字体、数据集、代码副本） | 授权与体积风险 |
| G9 | 一次提交包含**≥2 个独立意图** | 一个意图一个分支 |
| G10 | **同一提交混入他人/其它会话的工作** | 归属与评审责任不清 |
| G11 | 涉及**不可逆操作**（删除、迁移、force push、tag、发布） | 必须显式授权 |
| G12 | 首次在仓库引入**新工具链 / 新目录布局** | 结构性变化 |

### 2. 直推白名单（**必须全部**满足才可直推 `main`）

- W1 改动**单一意图**，且只触及**一个**功能域
- W2 净变更 **< 400 行**（不含测试、生成物、锁文件）
- W3 **不触及** G1–G12 任何一条
- W4 目标分支**未落后远端**（`git log --oneline HEAD..@{u}` 为空）
- W5 仓库为 **private**，且提交邮箱**是个人邮箱**（非公司域名）
- W6 提交前**验收命令全绿**（仓库 README / STATUS 中声明的那条）
- W7 工作树**干净**，无未跟踪的临时文件

> 白名单是**合取条件**，不是「取几条」。缺一条 → 开 PR。

### 3. 「开 PR」还是「先拆分」？

两者不矛盾，顺序是**先拆、再开**：

1. 若一次提交命中多条判据 → **先拆成若干「单一意图」分支**，每个分支自查白名单；
2. 每个分支**独立跑验收**、**独立开 PR**；
3. PR 描述里**必须写明**：本 PR 覆盖哪个意图、验收命令与输出、爆炸半径、与其他 PR 的依赖关系；
4. 合并顺序：先合**低爆炸半径**的（工具/测试/文档），最后合**高爆炸半径**的（公共接口、渲染核心、数据格式）。

### 4. 拆分粒度

- 一个 PR = **一个意图 + 一个可独立验收的最小集合**（含其测试与文档）
- 拆分顺序建议：**先工具与测试 → 再功能实现 → 最后文档与数据校准**
- 不得为了「PR 数量好看」而把**逻辑上不可分**的改动硬拆（例如渲染器的 bug 修复与其回归测试）

### 5. 越权与例外

- **未经用户明确授权，不得直推 `main`、不得 `gh pr merge`、不得改仓库可见性。**
- 「用户说『同步到 GitHub』」**不等于**授权直推：默认解释为「**开 PR 并请用户审**」；
  只有用户明确说「直接推 main / 不用 PR」才可直推。
- 用户事后要求补开 PR：允许**事后补一个指向已推提交的 PR** 作为审查留痕，但**不得改写已推送历史**（除非用户明确要求）。

### 6. 机械化检查（不靠自觉）

把本规则的判据做成**可执行脚本**，提交前跑一次，让「该不该走 PR」变成**退出码**而不是判断题。

> **本仓库是纯文档仓库（public）**：只放 `.md` 标准，**不放可执行脚本**，
> 也不引用任何内部仓库的具体路径（内部项目名属私有信息）。
> 门禁脚本由**各项目自行实现**并放在自己的仓库里；判据的**唯一真相源是本条规则**，
> 脚本只是它的实现——脚本与本条不一致时，以本条为准。

```bash
# 通用形态：判定「当前分支相对 @{u} 的改动能否直推」
#   退出码 0 = 满足直推白名单，可直推
#   退出码 2 = 必须开 PR（逐条列出命中的判据）
#   退出码 3 = 前置条件不满足（落后远端 / 工作树脏 / 身份不对）
```

规则来源：本文件规则 6.5。**任何 AI / 任何模型接手本工作区，都以本条为准。**
